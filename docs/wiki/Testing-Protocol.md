# Testing Protocol

How we check that Rembo actually reduces re-entry and errors, and that its security rules hold. The protocol runs mainly in **Sprint 6** ([Roadmap](Roadmap)). Results go into the handover package on 7 December.

## Hypothesis under test

> An expense flow adapted to Moroccan business rules reduces re-entry and errors.

We measure the gain with real users. We make **no promise about OCR accuracy**: we measure how many fields the user has to correct.

## Test material

- A set of **30 fictional receipts** of varying quality: clean, crumpled, faded, handwritten, with and without VAT and ICE, different categories. They are in the repository (`assets/bench/`, generated by `tool/bench/generate_receipts.py`), each with the values a reader should find (`assets/bench/manifest.json`): clean, blurred, faded, tilted, crumpled, in shadow, low resolution, handwritten, two in Arabic, two in foreign currencies
- The **OCR bench** in the app (Profile → « Banc d’essai OCR ») reads the 30 pictures on the phone, or with the server reader, and scores each field (supplier, ICE, date, amount, VAT, VAT rate, currency), by field and by quality of picture; the report is shared as a CSV. `test/bench_test.dart` runs the parser on the printed text of the same receipts and keeps its scores as a floor
- **Fictional data only**: no real employee, client or supplier data (see [Data Protection & Security](Data-Protection-and-Security))
- The Rembo app on **Android and iOS**, connected to a test Supabase project with seed data (companies, users per role, categories, policies)

## User tests

- Up to **5 target users** (employees, managers, accountants of Moroccan SMBs), depending on availability
- Each user processes receipts **with Rembo** and **with their current method** (paper, spreadsheet, email…)

| Measure | How |
|---|---|
| **OCR fields corrected** | For each receipt, number of fields the user had to fix (date, supplier, amount, currency, VAT, ICE). Collected by the app itself: Profile → « Mesures des agents » (SQL view `agent_metrics`) |
| **Time to declare** | From the picture (or the form opening) to the submitted expense, recorded by the app (`capture_started_at`); the current method is timed by hand |
| **Comparison** | Same measures with the current method |
| **Feedback** | Short interview after the session: what was easy, what was confusing, would they use it |

## Control checks

These must pass before demo day. Each one is a test case with a fictional scenario.

| # | Control | Expected result |
|---|---|---|
| C1 | **No self-approval**: an employee who is also a manager tries to approve their own expense | Refused by the app **and** by the database |
| C2 | **Receipt isolation**: user B tries to open user A's receipt (direct query and Storage URL) | Access denied by RLS and Storage policies |
| C3 | **Export consistency**: total of approved expenses vs total in the exported CSV | Totals are **identical**; every approved expense appears exactly once |
| C4 | **Escalation**: an expense above the alert limit, and an ambiguous receipt | Both are routed to a manager with the reason shown |
| C5 | **No secret on the client**: inspect the app build and the repository | Only the public `anon` key is present |

**Where each control is automated** (CI, job « Database & functions », and the scripts below):

| # | Test |
|---|---|
| C1 | `supabase/tests/database/02_approval.test.sql`, `07_controls.test.sql` (also a manager promoted afterwards, and the batch confirmation) |
| C2 | `07_controls.test.sql`: a colleague, the manager before submission and another company read no receipt; the manager reads it once submitted |
| C3 | `06_export_agent.test.sql` (count, total and VAT of the batch equal the approved ones; no second export); the app also compares them after each export |
| C4 | `07_controls.test.sql`, `04_compliance_agent.test.sql` |
| C5 | `tool/check_no_secrets.sh` on the repository and on the built APK |

The end-to-end journey (capture, correction, submission, decision) runs in `integration_test/journey_test.dart`, on a phone or in the CI.

## Reporting

Record the results in a test report (in the repository, under `docs/`):

- Receipts processed, fields corrected per receipt, time per declaration
- Comparison with the current method
- Results of controls C1–C5, with screenshots
- Known limits and bugs found (each bug becomes a `type: bug` issue)
